# Полный цикл тестирования AFFiNE

## Смысл

Доводи изменение до состояния, где проверен не только код, но и пользовательский сценарий. Для AFFiNE это обычно означает: понять затронутые слои, запустить узкие проверки, собрать локальный production-артефакт, поднять или обновить тестовый контур, пройти сценарий в браузере и зафиксировать остаточные риски.

## Базовый порядок

1. Прочитай проектный контекст: `AGENTS.md`, текущий `git status --short`, измененные файлы и ближайшие package scripts.
2. Определи затронутые контуры: backend, frontend, BlockSuite/editor, storage/blob, auth/permission, GraphQL/sync, bot, deploy/ops.
3. Сначала закрой инспекции и явные IDE/lint предупреждения, затем переходи к quality и тестам.
4. Запусти самый узкий релевантный unit/integration test (модульный/интеграционный тест), который подтверждает исправленную ветку поведения.
5. Запусти статические проверки для затронутых файлов: `lint:ox`, package-local lint, `yarn typecheck` или более узкий typecheck, если он существует.
6. Для UI или runtime-поведения выполни локальную production-сборку. Для deploy-пути собирай образ локально, без GitHub build.
7. Подними тестовый контур на случайном или явно свободном нестандартном порту.
8. Проверь реальный сценарий в браузере: загрузка страницы, действие пользователя, консоль, network, видимый результат, перезагрузка страницы при необходимости.
9. Если есть prod/deploy часть, проверь версию `/info`, состояние контейнеров/процессов и логи после сценария.
10. Перед финальным ответом перечисли: какие проверки запущены, какой результат получен, какой контур остался вне запуска.

## Выбор проверок

Используй узкие команды, затем расширяй контур по риску:

- Backend permission/sync/storage: package-local tests, GraphQL/API сценарий, серверные логи, negative case (запрещенное действие).
- Frontend/editor: affected package tests, typecheck, production build, браузерный сценарий с console/network наблюдением.
- Anonymous board: отдельная проверка гостевого/инкогнито контура, отсутствие authenticated cookies (аутентифицированных cookie), проверка прав на update/delete/upload.
- Image/blob: загрузка файла, отображение, reload, проверка blob URL/request status, проверка server log на permission/storage ошибки.
- Deploy: локальная сборка, доставка артефакта, `/info`, container health, smoke scenario (дымовой сценарий).
- Bot: локальная SQLite backup, dry-run где уместно, один реальный сценарий выдачи/отзыва ссылки, проверка записи в БД.

Если нужна подробная матрица, открой `references/test-matrix.md`.

## Браузерная проверка

Для пользовательских сценариев используй реальный браузерный контур: Browser plugin, Playwright или существующие e2e helpers проекта. Проверка считается содержательной, когда зафиксированы четыре факта:

- Страница реально открылась в нужном режиме пользователя.
- Действие пользователя реально выполнено.
- Видимый результат соответствует ожиданию.
- Console/network/server logs не содержат ошибок по проверяемому сценарию.

Для anonymous board отдельно проверяй приватный/гостевой режим и повторную загрузку страницы после действия. Для image upload проверяй, что изображение видно после загрузки и сохраняется после reload.

## Локальная production-сборка

Сборка для deploy выполняется локально. GitHub Actions (действия GitHub) подходят для быстрых checks (проверок) PR, но не заменяют локальную сборку в этом проекте.

Для тяжелых production-сборок фиксируй:

- commit hash (хеш коммита), из которого собран артефакт;
- target architecture (целевая архитектура);
- команду сборки;
- итоговый артефакт или image tag (тег образа);
- команду smoke-проверки после запуска.

## Работа с провалами

Если проверка падает, продолжай цикл:

1. Сузь отказ до слоя: UI event, client state, network, API, sync, storage, permission, deploy/runtime.
2. Добавь или исправь тест, который воспроизводит отказ в самом близком слое.
3. Исправь код.
4. Повтори узкую проверку.
5. Повтори браузерный сценарий, который пользователь фактически выполняет.

Финализируй задачу только после прохождения сценария, ради которого делалось изменение, или после явного решения владельца оставить конкретный риск.

## Финальный отчет

Финальный ответ должен быть коротким и проверяемым:

- Что изменено на уровне смысла.
- Какие проверки запущены и какие результаты получены.
- Какая версия/ветка/хеш проверены, если был deploy.
- Какой контур остался вне запуска и почему.

Не заменяй пользовательский сценарий unit-тестом, если пользователь жаловался на браузерное поведение. Не называй задачу завершенной до браузерной проверки соответствующего сценария.
